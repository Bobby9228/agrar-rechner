# ADR-001 — AppGlobals-Namespace für implizite Globals

- **Status:** akzeptiert
- **Issue:** #278 (Folgeissues: #418 Schritt 3, #447)
- **Datum (Einführung):** Phase 5 (Stand 2026-06-15, Refactor-Welle #418)

## Kontext

Die App wird seit der ersten Ausgabe als statische PWA ohne Build-Step aus
einer Reihe von `<script src="…">`-Tags am Ende von `index.html` gestartet.
Dadurch hängt die Reihenfolge der Module direkt zusammen: jede Datei
verlässt sich darauf, dass vorherige Module ihre Variablen bereits in den
impliziten `window`-Scope geschrieben haben (`var state = …`,
`function addReiter() { … }`, etc.). Cross-File-Calls wie
`addReiter()` aus einem anderen Modul funktionieren nur, weil jedes
Modul den gleichen Namespace teilt.

Dieser implizite Window-Scope ist die Wurzel mehrerer realer Probleme:

- **ESM-Migration blockiert.** Sobald ein Modul auf
  `import { x } from './y.js'` umgestellt wird, bricht der gemeinsame
  Namespace — `window.x` ist dann nicht mehr definiert, und Tests, die
  genau das prüfen, laufen rot. Die Migration bleibt deshalb bewusst
  hinter einem konkreten Trigger (siehe `AGENTS.md` §5 Out of scope).
- **ESLint `no-undef` produziert 348 Fehler.** Die Regel kann nicht
  wissen, dass `state` zur Laufzeit vorhanden ist, weil die Datei
  `state.js` sie erst beim Boot als globales `var` definiert. Ergebnis:
  Tausende false-positive Errors, die das Refactor-Tempo ausgebremst
  haben (siehe `eslint.config.js` Begründung).
- **Lesbarkeit leidet.** Ein Aufruf wie `getActiveReiter()` ohne
  erkennbares Modul-Präfix ist im Editor schwer zuzuordnen.

## Entscheidung

Wir führen **eine** zentrale Namespace-Konvention ein: `AppGlobals`. Sie ist
explizit, geteilt und wird am Dateiende jedes Moduls via
`Object.assign(window.AppGlobals, …)` befüllt.

1. **Initialisierung in `public/js/app-globals.js`.** Diese Datei wird
   als allererstes Modul geladen (siehe Lade-Reihenfolge in
   `README.md`). Sie definiert
   `var AppGlobals = window.AppGlobals = {}` und richtet
   `AppGlobals.state` als Live-Alias für das später von `state.js`
   definierte `var state` ein (`Object.defineProperty`-Getter/Setter).
   Damit bleibt der historische Direkt-Zugriff auf `window.state`
   für Debug-Zwecke erhalten; Event-Bindings laufen seit #418
   ausschließlich über `addEventListener` (keine Inline-Handler im
   Markup — deshalb kommt die CSP ohne `'unsafe-inline'` aus).

2. **Registrierung am Dateiende.** Jedes andere Modul exportiert seine
   Funktionen/Konstanten am Dateiende über
   `Object.assign(window.AppGlobals, { … })`. Eine zentrale
   Reihenfolge-Klausel: Konsumenten greifen NUR über
   `AppGlobals.funktionsName()` zu, nicht über
   `window.funktionsName()`. Inline-Event-Handler im HTML-Markup
   sind seit #418 vollständig entfernt (#449-Verifikation: 0 Treffer
   auf `\son[a-z]+=` in index.html); neue Bindings erfolgen
   ausschließlich per `addEventListener`.

3. **`AppGlobals.state` ist absichtlich kein Plain-Property.** Wegen
   Reassignments durch `loadState()` und die Cross-Tab-Sync-Bridge
   bleibt der Live-Alias ein Getter/Setter. Wer in `state.js` versehentlich
   `state: state` in den `Object.assign`-Block schreibt, würde den
   Getter mit einem Plain-Property überschreiben und die Reassignments
   brechen — das wird im Header-Kommentar von `state.js` ausdrücklich
   dokumentiert.

4. **ESLint-Konfiguration folgt.** Sobald die Migration steht, wird
   `no-undef` für `public/js/**` re-enabled (Stand 2026-06-15: 0
   Errors, siehe `eslint.config.js`).

## Konsequenzen

**Positiv:**

- `no-undef` ist reaktivierbar; die Modul-Grenzen sind statisch prüfbar.
- Cross-File-Abhängigkeiten werden im Editor sichtbar (`AppGlobals.X` →
  springt zur Definition).
- ESM-Migration wird trivial: ESM-Imports ersetzen die AppGlobals-Reads
  1:1, weil sie unter dem gleichen Namen exportiert werden können.
- Tests können Modul-Surfaces einzeln mocken (`AppGlobals.X = mockFn`).

**Negativ / Trade-offs:**

- Der Window-Scope bleibt **teilweise** offen (`var state` aus
  `state.js` als Debug-Zugriff, `var AppGlobals` selbst sowie die
  übrigen Top-Level-`var`/`function`-Deklarationen der Module). Für
  Event-Bindings ist er seit #418 geschlossen (alle Bindings via
  `addEventListener`); eine vollständige Scope-Schließung wäre erst
  eine ESM-Migration.
- Zwei Alias-Wege (AppGlobals + window.AppGlobals) sind nötig, weil
  `Object.assign(window.AppGlobals, …)` ein gemeinsames Objekt
  garantiert; andere Schreibweisen würden das brechen.

**Offene Trigger für eine ESM-Migration** (steht nicht in dieser ADR):

- Refactor von AppGlobals in mehrere kleine Namespaces
  (z. B. `AppGlobals.Calculations`, `AppGlobals.Render`).
- Bundler-Einführung — explizit abgelehnt in `AGENTS.md` §5.
- Bedarf an Tree-Shaking bei wachsender Modulanzahl.
